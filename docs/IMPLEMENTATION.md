# MoonTFM 如何实现，以及怎样检查效果

本文通过八项实际 CLI 演示说明源码职责、字节布局、关键计算和预期结果。演示运行不依赖 TeX。

## 先运行，再读源码

在项目根目录的 PowerShell 执行：

```powershell
./scripts/bootstrap.ps1
moon build --target js --release --deny-warn
node scripts/demo.mjs
```

也可使用 `npm run demo`。演示脚本分别运行每项命令的文本和 JSON 版本，用手工设定的期望值检查实际报告。输出写入忽略的 `artifacts/demo/report.md` 和 `report.json`。报告包含执行时间、源码提交、工作区状态、编译产物哈希、输入文件哈希、每个检查项及原始子进程输出。

`node scripts/demo.mjs --list` 列出案例；`node scripts/demo.mjs --case bad-lig-entry` 单独运行入口越界案例；添加 `--json` 输出完整机器报告。报告每次覆盖，以最后一次运行选择的案例为准。

| 案例 ID | 你应看到什么 | CLI 退出码 |
|---|---|---:|
| inspect | 正常文件为 15 字、设计字号 10pt，存在字符 65 | 0 |
| glyph | 字符 65 的宽度为 524288，即 0.5 个设计字号单位 | 0 |
| bad-index | 字节 32 的宽度索引 250 越界，合法范围 0—1 | 2 |
| bad-lig-entry | 字节 62 的实际入口 65535 越界，关联字符 65 | 2 |
| width-change | 字符 65 的宽度从 524288 变为 655360 | 1 |
| table-reorder | 字符度量不变，但 char_info 与宽度表发生变化 | 1 |
| zero-width | 字符存在，宽度恰好为零 | 0 |
| missing | 字符 66 不存在，metrics 为 null | 0 |

这些业务退出码不同，不表示演示失败。演示脚本会核对每个退出码和字段，全部匹配时自己退出 0；任一不匹配时退出 1，并保留实际结果供检查。正常验收应看到 `8/8 项符合预期`。

## 数据从哪里流到哪里

```mermaid
flowchart LR
  A[TFM 文件字节] --> B[Node CLI：参数与有界读取]
  B --> C[MoonBit parse：布局与各表]
  C --> D[MoonBit validate：结构与引用]
  D --> E[glyph 查询或 diff 比较]
  E --> F[MoonBit JSON 报告]
  F --> G[CLI：JSON 原文或文本展示与退出码]
```

日常运行时，文件输入和文本排版由 Node.js 负责，解析、校验、度量查询、差异计算及 JSON 报告由 MoonBit 完成。`cmd/main/main.mbt` 只导出三个 JS ABI 包装函数，Bytes 对应 Uint8Array；Node 传入读到的字节，没有另写一份 TFM 解析器。

| 源码 | 主要职责 | 检查重点 |
|---|---|---|
| [bin/moontfm.mjs](../bin/moontfm.mjs) | 四个命令、读取文件、文本展示、退出码 | 错误不会伪装成成功，输入最多读取 131069 字节 |
| [parser.mbt](../parser.mbt) | 有界布局解析与字符度量查询 | 先校验目录和真实长度，再读取各表 |
| [model.mbt](../model.mbt) | Font、Character、Metrics、Diagnostic 等数据类型 | 原始整数、存在性与可空字段明确区分 |
| [validate.mbt](../validate.mbt) | 表索引、尺寸、字符引用、入口、配方和循环检查 | 字符入口和纯边界声明按不同上下文校验 |
| [diff.mbt](../diff.mbt) | 按字符实际度量比较，并保留其他表变化 | 表布局不同不能误报字符度量变化 |
| [report.mbt](../report.mbt) | 解析、校验和查询的 JSON 信封 | invalid 与 ok 分开，始终说明检查范围 |
| [scripts/demo.mjs](../scripts/demo.mjs) | 运行实际命令并逐项验收 | 不把手写预期文字当作实际输出 |

## 手工检查一个 60 字节文件

`fixtures/minimal.tfm` 的目录含 12 个大端 16 位整数。头两个数为 lf=15、lh=2，含义是总长 15×4=60 字节、头数据 2×4=8 字节。

| 字节区间，含端点 | 内容 |
|---|---|
| 0—23 | 12 项目录 |
| 24—31 | checksum 和设计字号 |
| 32—35 | 字符 65 的记录 |
| 36—43 | 两项宽度 |
| 44—51 | 两项高度 |
| 52—55 | 深度零项 |
| 56—59 | 斜体修正零项 |

字符记录是 `01 10 00 00`。第一字节 01 表示宽度索引 1；第二字节 10 的高四位为高度索引 1，低四位为深度索引 0；第三字节的高六位为斜体索引 0，低两位为 tag=0。查询宽度时实际读取宽度表第 1 项，即字节 40—43 的 `00 08 00 00`，值为 524288。

度量保存为有符号 12.20 定点整数，展示时除以 1048576：524288/1048576=0.5。设计字号为 10pt，因此在设计字号下对应宽度是 5pt。内部比较直接比较 524288 等原始整数，不依赖十进制展示值，负数深度和 kern 也不会被统一当作损坏。

字符是否存在根据宽度索引是否非零判断，而不是根据宽度数值是否为零。这就是 zero-width 和 missing 两个案例必须分别检查的原因。

## 连字入口与边界声明的校验

lig/kern 表首记录的 skip=255 可用来声明右边界字符。但字符的 tag=1 若恰好引用同一条记录，TeX 会把它当作入口重启记录，需要解析实际地址。

校验器分别处理两种上下文：先遍历现有字符，检查直接入口；若入口 skip>128，则计算 `256*c+d` 并检查实际目标。随后遍历控制记录，校验普通记录和左边界地址；已由字符入口检查的错误不再重复报告。没有被字符引用的纯右边界声明保留原本合法行为。

反例中直接入口为 0，看似在两项表内；但该记录的 c=d=255，实际地址为 65535，必须报错。地址字段从字节 62 开始，因此诊断指向 byte_offset=62，并给出 character_code=65、actual=65535 和合法范围 0—1。

skip=128 是普通停止操作；大于 128 才在字符入口重启一次。重启后遇到控制停止记录不递归追跳转。这里校验的是地址结构，没有执行完整连字程序。

## 差异报告怎样避免误报

`diff` 先校验两个字体，再对 0—255 每个字节编码查询实际四类度量，分别记录新增、移除和改变。设计字号单独比较。table-reorder 案例将宽度索引从 1 改为 2，但新索引仍指向 524288，因此没有字符度量变化。

同时，原始 char_info 和宽度表确实改变了，报告保留 `other_changes=["char_info","width_table"]`。`metrics_equal=true` 只说明设计字号和字符度量相等；CLI 返回 1 表示仍发现了原始变化，不把它声称为整个字体完全等价。

## 安装脚本怎样保证版本一致

[bootstrap.ps1](../scripts/bootstrap.ps1) 从 moon-toolchain 读取完整版本，并分别核对编译器实际输出与标准库 moon.mod 中的版本。[toolchain-state.ps1](../scripts/toolchain-state.ps1) 负责版本识别、暂存解压、校验新版本、替换目录及失败时恢复旧标准库。错误归档不应移除原标准库，旧源码和缓存也不能残留进新版本。

对应六个状态测试位于 tests/bootstrap-cases.ps1，覆盖版本识别、旧库替换、错误版本、损坏 ZIP 和首次安装。它们只在 Windows 执行；Linux CI 会明确跳过这六项，其余核心和 CLI 测试照常运行。

## 检查效果时的边界

本项目检查经典 8 位 TFM 的结构和引用，不渲染字形。演示中看到的是字体度量和诊断，不是字符图形或页面排版效果。完整连字执行语义、JFM/OFM 等范围仍未实现，报告中的 not_covered 会持续披露这些限制。
